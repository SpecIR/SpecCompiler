# Mutation Testing Framework

Mutation testing for SpecCompiler's SQL verification views and Lua pipeline source.
Measures test suite effectiveness by injecting faults and checking if tests detect them.

## Quick Start

```bash
# SQL analyze-query mutations (safe, in-memory — ~10 min)
./tests/mutation/mutate.sh --sql

# Lua source mutations on a specific file (~2-10 min depending on file size)
./tests/mutation/mutate.sh --lua src/pipeline/analyze/analyze_handler.lua

# Verbose: show killed mutants too (not just survivors)
./tests/mutation/mutate.sh --sql --verbose
```

Reports are written to `tests/reports/mutation/sql_report.json` and `lua_report.json`.

## How It Works

### SQL Mode (`--sql`)

Mutates SQL analyze-query view definitions **in-memory** (never writes to disk). For each of the
25 analyze queries (16 default + 9 sw_docs), applies single-site mutations and checks whether the
`verify`/`casting_negative` fixtures detect the change.

**Operators** (6): negate EXISTS, relax AND→OR, flip comparisons, swap NULL checks,
shift HAVING thresholds, drop WHERE predicates (paren-balanced: dropping `AND NOT EXISTS (`
removes the whole subquery, so every mutant is valid SQL).

**Oracle**: the multiset of `(policy_key, file, line)` diagnostics of every fixture is compared
against a baseline. Any difference kills the mutant. Comparing locations, not only counts,
means that a mutant which swaps *which* objects are flagged is detected even when the count
is unchanged (e.g. `NOT EXISTS` → `EXISTS` with one violation and one control object).

**Baseline**: every fixture is compiled twice and the second signature is the baseline; a
policy_key whose count differs between the two passes is reported as unstable and excluded
from the oracle for that fixture. External render outputs (`build/mutation/diagrams`) are
deleted before every compilation so that a failed render is reproduced on every run
(a leftover output would otherwise be taken as a cache hit). Set
`MUTATION_KEEP_RENDER_CACHE=1` to skip that deletion.

**Classification** of each mutant:

- `killed` — a fixture's diagnostics differ from the baseline (`kill_reasons.diagnostics`), or
  the pipeline crashed (`kill_reasons.crash`).
- `stillborn` — the mutated view cannot be created or queried (invalid SQL). Excluded from the
  total: an invalid mutant says nothing about the fixtures.
- `duplicate` — identical SQL already generated by another operator. Excluded from the total.
- `equivalent` — survived, and listed in `tests/mutation/sql_equivalents.lua` with a written
  justification. Excluded from the score denominator.
- `survived` — survived and not classified. These are the test gaps.

**Score** = killed / (total − equivalent). The report (`sql_report.json`) also carries
`per_operator`, `per_view`, `survivors` (with the mutated SQL), `equivalents`, `stillborns`,
`duplicate_list`, `kills` (with the killing fixture and the diagnostic diff), the baseline
signature per fixture and any unstable codes. `MUTATION_REPORT_DIR` overrides the report
directory.

### Lua Mode (`--lua <file>`)

Mutates a Lua source file **on disk** (writes mutated file, runs tests, restores original).
A shell trap + backup file protects against interrupted mutations leaving corrupted source.

**Operators** (10): flip equality/order/logic/bool, remove not, nil→false, flip return,
off-by-one, boundary shift, empty string.

**Oracle** (triple-signal): Any change in (1) output file content, (2) diagnostic keys,
or (3) pipeline pass/fail status kills the mutant. Mutations are pre-validated with
`load()` to skip syntactically invalid mutants.

## Architecture

```
tests/mutation/
  mutate.sh           Shell entry point (env setup, safety trap, argument parsing)
  mutator.lua         Pandoc filter: orchestrates baseline, mutation, comparison
  sql_operators.lua   SQL mutation operator catalog (6 operators)
  lua_operators.lua   Lua mutation operator catalog (10 operators)
```

The engine runs as a Pandoc Lua filter (`pandoc --lua-filter tests/mutation/mutator.lua`)
to reuse the same Lua/Pandoc runtime as the SpecCompiler pipeline. This enables in-process
execution via `engine.run_project()` without subprocess overhead.

## Safety

- **SQL mode**: Mutations are injected into `package.loaded` (Lua module cache). No files
  are written. Safe to run anywhere, anytime.
- **Lua mode**: Mutates the source file on disk. Protected by:
  1. `mutate.sh` creates a `.mutation_backup` file before starting
  2. A shell `trap` on EXIT/INT/TERM restores from backup if the source was left mutated
  3. `mutator.lua` restores the original source after the mutation loop completes
- **Normal test suite**: The mutation framework is completely isolated. `tests/run.sh`
  never discovers or invokes it. It must be run explicitly via `mutate.sh`.

## Interpreting Results

- **Survivors**: Mutations the tests didn't catch. Each survivor is either:
  - A **test gap**: real weakness — add a fixture that exercises this code path
  - An **equivalent mutant**: the mutation doesn't change observable behavior
    (e.g., `nil → false` when callers only check truthiness). SQL equivalents are
    recorded, with a justification, in `sql_equivalents.lua`; the score excludes them.
- A score of 100% with an empty equivalents list is a warning sign, not a result: every
  operator produces some equivalent mutants (see the reviewer's remark that motivated the
  location-aware oracle and the equivalents catalogue).
- **Kill signals** (Lua mode): Reports which signal detected each mutant:
  - `output`: the generated document changed (most common for pipeline code)
  - `diagnostics`: error/warning codes changed (common for verify/validation code)
  - `status`: the pipeline crashed (rare but definitive)
